# 验收：证据规则

> **工人的自述不是证据，我复现出来的输出才是。**

## 每个产出的固定动作（唯一定义；记录表格见 `templates/acceptance.md`）

1. **复跑检查命令**（格式化 / 静态检查 / 测试），看**真实输出**，不看工人贴的。
   - **切片收尾（闸门 C）必须跑全量。** 工人的检查**限定到本包**（避免与并行窗口互相干扰），所以**只有我能做累积回归**——不跑这一步，第 8 片破坏第 2 片的行为要到收尾才发现。
   - 有其它窗口正在跑时，等它收尾再跑；实在等不了就**记入未验证清单**，并将该片标为「待验收」。补跑全量门禁并通过之前，台账和切片计划都不得写「已验收」。
2. **看 Git 状态——不能只看提交。** 共享分支上的 `基线..HEAD` 里混着别的窗口的提交，**它不等同于这个工人的产物**。
   - **开窗前**在台账记下**基线状态**：SHA + `git status` + 已有的未提交差异。不记就无法归因。
   - **收尾时看三样**：`git log --oneline <基线>..HEAD`（提交）+ `git diff --cached`（已暂存）+ `git diff`（未暂存）。只查提交会漏掉暂存与未暂存的改动；只查 HEAD 会漏掉本窗口的早前提交。
   - **与工人交接里列的 SHA 与路径逐条核对**——对不上就是有问题（夹带、漏报、或另一个窗口的提交混了进来）。
3. **抽查实现**：挑本轮文件读源码，核对是否真按决策写的（而不是糊了个能编译的空壳）。
   **数量随规模与风险调整**：单文件切片抽 1 个就够；多文件 / 跨模块 / 高风险抽 ≥2 个，且**必抽**承载核心不变量的文件。
   抽查是**抽样**的——它拦不住逻辑 bug，所以第 4 步不可省。
4. **对核心不变量，自己写反例**（见下）。
5. 把以上真实输出写进验收记录。

## 验收强度要匹配风险

工人测的是"我实现了"，我要测的是"它会不会在 X 情况下崩"——**只跑工人的测试是不够的**。

| 风险 | 验收动作 |
|---|---|
| 低（文档、命名、格式化） | 跑检查命令 + 扫一眼 |
| 中（普通业务逻辑） | 上面 + 抽查实现 |
| **高（数据正确性、并发、崩溃恢复、安全）** | 上面 + **自己写对抗性反例** + **负面测试** |

**反例怎么设计**：

- 从**不变量**出发，不是从代码出发。问"这条不变量在什么情况下会被违反？"，然后**造那个情况**。
- 典型角度：并发（N 个同时）、中断（在任意两步之间杀）、重复（同一输入两次）、极端值（空 / 超大 / 非法）、**顺序**（谁先谁后）。
- **照行为重写的算法**（把某个实现按行为复刻过来）："够"的判据是**能与参考实现的中间量逐字段对上**，不是"端到端输出像"。只比得出端到端结果时，明确降级为未验证——**别用"体积量级相当"充数**。实测：一个复刻算法带着 22 个全绿的测试通过了，而它的中间量错了一处（一个乘积溢出饱和），只有逐字段比对才查得出。
- **负面测试**：故意制造违规，断言它**必须失败**（编译错误、非零退出码），然后还原。例：断言"分层是编译期约束"——造一次违规，确认编译失败。

**测试全绿 ≠ 能用。** 一定要区分"我验证了"与"我无法验证"，后者进未验证清单。

## 三条硬约束

1. **验收文档只能由命令输出填充。** 顺序必须是「跑 → 贴」。**先写输出再去跑就是编造证据。**
2. **验收命令不得让 `grep` 决定成败。** `cargo test | grep ...` 的退出码是 grep 的——要么检查失败标记是否存在，要么开启管道失败传播。
3. **"通过"必须有可见的判据。** 不是"看起来对了"，而是"这条命令、这个输出、这个退出码"。

## 退回协议

- 同一窗口**续轮**下修正指令。修正指令必须指名"哪个文件、哪一行行为不对、期望是什么"。
- **次数不是硬上限**：续轮到**第二次仍不过**时，停下来重新判断——**是规格写坏了，还是实现不行？** 规格问题就改规格（可能一次就过）；实现问题才换人。
- 换成我自己修、或换窗口重写该文件时，记一条"该实现由人接管"。
- **退回原因必须记录**——这是判断工人可靠性的唯一依据。

**先分清责任**：退回前先问"是不是我的规格写坏了"。工人自己的测试抓出的 bug 归工人，规格矛盾归我——**把这两种混为一谈，会既冤枉工人也放过自己。**

## 外部核验的产物要求

派**外部核验型**子代理（确认某外部系统现在能不能用）时，产物必须含三样，缺一不算验过：

1. **能不能用**的判定（能 / 不能 / 有条件能）。
2. **最小可用调用**：真实的请求与**真实响应**（不是"文档上说"）。截断敏感字段，但保留可判断的形状。
3. **坑**：实际调用中遇到的意外（限流、字段缺失、鉴权方式、版本差异）。

**熔断**：先确认能拿到什么（凭据 / 网络 / 额度），拿不到 ⇒ **明确降级为调研型**并记入未验证清单，**不许假装验过了**；对外只读、单次、不批量、不写，有副作用的先问用户——核验的成本不该包括被封号；核验要写文件时写在**记录目录或临时目录**，不要污染被构建仓库。

**未验证清单里每一项都该先过这一问**：能不能派一个外部核验型子代理，把它从"未验证"变成"已验证"？

## 我自己的上下文

**流程管理了工人的上下文，但架构者（我）的上下文也要管理**——而它没有自动压缩点。

**办法：把结论落成压缩后的文档，然后停止回读细节。**

- 每片收尾时，把该片结论写进**总纲 / 切片计划 / 缺口表**——这三份是**我的外部记忆**。
- 继续下一片时**只读这三份**，不回读流水与验收记录。需要复核某个具体判断时才回读。
- **做不到"只读三份就能继续"，说明记录写得不够压缩**——那是记录的问题。

**该警惕的信号**：我开始重复问同一个问题、开始忘记某个已作的决策、开始凭印象而不是凭文件说话。
