# 验收：证据规则

## 每个产出的固定动作（唯一定义；记录表格见 `templates/acceptance.md`）

1. **复跑检查命令**（格式化 / 静态检查 / 测试），看**真实输出**，不看工人贴的。
   - **在派工前规定门禁范围**：heavy 每片跑全量；lite 每片可跑本轮与受影响已完成切片的检查，注明影响范围依据，无法可靠圈定时跑全量。两档在集成节点与最终交付都跑全量。工人的检查尽量限定到本轮范围，累积回归由我负责。
   - **验收对应稳定的代码状态**：记下 SHA、未提交差异、命令、环境与门禁范围；检查期间暂停会改变被测状态的写入，或在独立快照中运行。同一状态的全量结果可复用；后续代码、配置或依赖变化后，重跑受影响检查，最终证据须覆盖交付状态。
   - 与其它工人的检查或写入存在共享资源冲突时，先等待或隔离；无法完成规定门禁则列入未验证清单，切片标为「待验收」。规定证据补齐前不得写「已验收」。
2. **看 Git 状态——不能只看提交。** 共享分支上的 `基线..HEAD` 里混着别的工人的提交，**它不等同于这个工人的产物**。
   - **派工前**在台账记下**基线状态**：SHA + `git status` + 已有的未提交差异。不记就无法归因。
   - **收尾时核对全部改动形态**：`git log --oneline <基线>..HEAD`（提交）+ `git diff --cached`（已暂存）+ `git diff`（未暂存）+ `git status --short --untracked-files=all`（含未跟踪文件）。另外核对交付物是否落入忽略规则；需要时对交付路径运行 `git check-ignore`。未跟踪或被忽略的文件不出现在普通 diff 里。
   - **与工人交接里列的 SHA 与路径逐条核对**——对不上就是有问题（夹带、漏报、或另一个工人的提交混了进来）。
3. **抽查实现**：挑本轮文件读源码，核对是否真按决策写的（而不是糊了个能编译的空壳）。
   **范围随规模与风险调整**：覆盖承载核心不变量的代码及跨模块边界；单文件切片读该文件，不设超过实际文件数的抽查下限。
   抽查是**抽样**的——它拦不住逻辑 bug，所以第 4 步不可省。
4. **按风险验证不变量**，高风险核心不变量由我独立设计反例（见下）。
5. 把以上真实输出写进验收记录。

## 验收强度要匹配风险

工人测的是"我实现了"，我要测的是"它会不会在 X 情况下崩"——**只跑工人的测试是不够的**。

**每条不变量都要对应验证方法与可定位证据**：可采用行为测试、静态检查、类型约束、形式化证明或源码审查。选能判定该条要求的方法；无法验证时列为未验证，不因存在一个测试就认为已证明。对高风险核心不变量，我另设计至少一个独立反例；存在「必须拒绝」的要求时补负面测试。

| 风险 | 验收动作 |
|---|---|
| 低（文档、命名、格式化） | 跑检查命令 + 扫一眼 |
| 中（普通业务逻辑） | 上面 + 抽查实现 |
| **高（数据正确性、并发、崩溃恢复、安全）** | 上面 + **自己写对抗性反例**；有拒绝要求时加负面测试 |

**反例怎么设计**：

- 从**不变量**出发，不是从代码出发。问"这条不变量在什么情况下会被违反？"，然后**造那个情况**。
- 典型角度：并发（N 个同时）、中断（在任意两步之间杀）、重复（同一输入两次）、极端值（空 / 超大 / 非法）、**顺序**（谁先谁后）。
- **算法重写按契约选择等价层级**：要求复刻内部算法时，比对约定的中间量，无法观察的部分列为未验证；只要求外部行为等价时，按输出、误差界限与不变量验证，不要求不同算法拥有相同中间状态。不能用「体积量级相当」代替正确性判据。
- **负面测试**：故意制造违规，断言它**必须失败**（编译错误、非零退出码），然后还原。例：断言"分层是编译期约束"——造一次违规，确认编译失败。

**测试全绿 ≠ 能用。** 一定要区分"我验证了"与"我无法验证"，后者进未验证清单。

## 三条硬约束

1. **验收证据先产生再记录。** 命令结果必须「跑 → 贴」；源码抽查与裁决要附可定位的依据。不得预写尚未观察到的结果。
2. **验收保存原检查命令的退出状态。** 过滤前保存输出与退出码，过滤器退出码或「未找到失败字样」不能证明检查通过；shell 支持时可启用管道失败传播，仍须能确定哪一步失败。
3. **"通过"必须有可见的判据。** 不是"看起来对了"，而是"这条命令、这个输出、这个退出码"。

## 退回协议

- 按 `references/delegation.md`「复用工人还是启用新工人」选择接手者。修正指令必须指名"哪个文件、哪一行行为不对、期望是什么"。
- 同一实现续轮到**第二次仍不过**时，先重新判断规格与实现的责任，再决定接手方式；这不替代冻结方案的整体预算上限。
- 换成我自己修、或换工人重写该文件时，记一条"该实现由人接管"。
- **退回原因必须记录**，包括失败证据及规格、实现、环境或并行干扰的归因。

**先分清责任**：规格矛盾归规格，实际实现偏离正确规格归实现，环境与并行干扰单独记录。工人主动在验收前发现并修复的问题，记录修复及测试证据，不等同于验收退回。

## 外部核验的产物要求

派**外部核验型**子代理（确认某外部系统现在能不能用）时，产物必须含三样，缺一不算验过：

1. **能不能用**的判定（能 / 不能 / 有条件能）。
2. **最小可用调用**：真实的请求与**真实响应**（不是"文档上说"）。截断敏感字段，但保留可判断的形状。
3. **限制与意外**：实际遇到的限流、字段缺失、鉴权或版本差异；没有意外就写「未观察到」，不强求编出问题。

**熔断**：先确认凭据、网络、额度与操作授权，拿不到就降级为调研型并列入未验证清单。默认用最小只读调用核验；额外付费或外部写入按 `SKILL.md` 的授权判据执行，已有授权不重复索取。核验文件写入获准的记录目录或临时目录，避免混入实现文件；仅依据文档不能声称已实际调用。

**结论与我强耦合、而我复核不了关键一环 ⇒ 不要外包理解本身。**

**未验证清单里每一项都该先过这一问**：能不能派一个外部核验型子代理，把它从"未验证"变成"已验证"？

**办法：把结论落成压缩后的文档，然后停止回读细节。**

- 每片收尾时，把结论写进总纲与缺口表；lite 更新总纲内的进度、台账与验收节，对照 `docs/freeze-plan.md §5` 的切片路线图，heavy 则更新切片计划。
- 继续下一片时先读上述压缩记录，具体判断有疑问时再回读流水与验收记录。若仍无法继续，就补足压缩记录。
