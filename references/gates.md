# 闸门与记录系统

> **每个闸门都有固定形状的工件**——没有工件，闸门会退化成"我觉得可以了"。

## 开始前 · 档位与预算

写契约或派独立复核者之前，先建 `docs/freeze-plan.md` 草案，填 §0 与 §8：建议档位、计数起点、轮次定义、连续失败重估点及整个任务的轮数、时间或资源上限。其余节可待契约复核后补齐；草案不等于实现授权，授权判据见 `SKILL.md`「闸门」。

预算从此处开始覆盖规格、复核、派工与返工。冻结时登记已用预算与剩余额度，不重置计数；触及上限先重估，不能通过换人或重划切片清零。预算不足时按闸门 D 交付部分完成；调整预算仍遵守用户已定上限，增加用户成本前取得所需决定。

## 闸门 A · 方案冻结

工件 = `templates/freeze-plan.md`，**落盘在被构建仓库的 `docs/freeze-plan.md`**——工人只读「仓库内文件 + 交接目录」，放进记录目录里工人就读不到边界。

两条最常被省掉的：

- **非目标**——比目标更能防范围漂移。
- **本机无法验证清单**——**冻结时就写**，不要收尾才发现。否则用户会把"检查全绿"读成"能用"。

冻结时补齐草案，核对「开始前 · 档位与预算」中登记的预算仍足以承担后续工作。

授权形态与档位选择见 `SKILL.md`「闸门」。

用户对冻结方案的决定若改变行为契约，先更新契约并重做受影响的规格自检，以及当前档位要求的独立复核，再派实现工人。

## 闸门 B · 变更（带代价核算）

发现变更会影响在途工人的动作时，先通知暂停受影响动作并确认，再修订方案或做契约复核。暂停只针对受影响范围；拿不到暂停确认时，停止对应任务并核对工具、子进程及外部作业的实际状态，无法确认的部分列为未验证。不得把「已发送暂停」写成「已停止」。

范围或架构变更需记录：① **一条 ADR**（heavy 写在 `orch-doc/01-决策记录.md`；lite 写在合并总纲的决策节）② **作废清单**（哪些既有决策 / 文件 / 计划失效）③ **代价核算**（作废了多少已完成工作、已花多少轮次）。

**只有影响用户承诺 / 成本 / 权限的变更才需要用户决定**——改变了交付范围、增加了花费、动了权限或外部可见契约。纯内部架构调整记 ADR 并通报，不设用户批准等待；受影响动作仍按本节暂停与恢复，无关工作继续。

> **变更史只在一处**：ADR 是权威；总纲的「范围与变更史」是**索引**；`docs/freeze-plan.md` 保留当前有效方案与决策索引，不另记变更史。

**不核算代价的变更 = 让用户闭着眼付账。**

> **变更若改了工人要遵守的约束**（契约里的不变量、失败分类、目录边界），必须**同时更新 `docs/<契约>.md` 或 `docs/freeze-plan.md`**——ADR 在 `orch-doc/` 里，工人读不到（见 `templates/AGENTS.md §1`）。只写 ADR 等于没通知工人。

行为契约改变时，重做受影响的规格自检及当前档位要求的独立复核。取得所需决定后，下发生效版本、差异和恢复范围，工人确认后才恢复受影响动作、验收该片或派发依赖工作。原会话无法同步时，核对其停止状态后按交接派新工人；旧任务停止情况未确认前，不让新工人争用相同资源。已验收切片按作废清单重验。

## 闸门 C · 切片收尾（默认不问用户）

产出 = 验收记录（`templates/acceptance.md`）。**填充纪律见 `references/verification.md` 的三条硬约束。**

**这一关由我按 `references/verification.md` 第 1 步复跑门禁**，覆盖本片与受影响的已完成切片。

验收记录标明对象是工人产物还是整合后的目标状态；状态与证据索引按下文「切片状态与整合记录」更新。

从 lite 升为 heavy 时，拆分合并记录并保留原证据位置，对已验收切片补齐新档位要求的验收证据；发现问题只重做受影响的部分。

**已授权范围内不问用户**；验收发现需要未授权操作或改变已承诺行为时，转闸门 B，按 `SKILL.md` 的授权判据取得所需决定。

**后续决策改动了已验收的产物时**：按 `references/delegation.md`「复用工人还是启用新工人」选择接手者；改动后按验收规则重跑门禁，并在该片的验收记录里**追加「修订」节而不覆盖原文**。

## 闸门 D · 最终验收（**交付，不是再等一次批准**）

① 最终代码状态下的门禁结果（全量与证据复用要求见 `references/verification.md`；未能运行也要写明原因）② **未验证清单逐条交付**，每条写清"为什么没验"与"怎么才能验" ③ **完成定义判定**：达标报「完成」，有阻断项报「**部分完成**」。

这一关**不设等待**——A 已经授权过，B 管变更，D 只是把结果交出去。用户看到「部分完成」或未验证清单后自行决定下一步。

**完成定义**：

- [ ] 当前范围内每个切片在目标工作区的验收通过，判定见「切片状态与整合记录」
- [ ] 关键用户流程的最终验证符合 `references/verification.md`「关键用户流程」要求
- [ ] **没有阻断项**（见下）
- [ ] 未验证清单已交付用户

**缺口分两类，只有一类阻断完成**：

| 类 | 判据 | 对"完成"的影响 |
|---|---|---|
| **阻断** | **未满足当前验收标准**的缺口 | **阻断**。此时只能报「**部分完成**」——**即使每项都写了"何时补"** |
| **可接受** | 已**明确移出当前范围**，或用户**已接受的限制** | 不阻断，写明接受范围、理由、依据或接受者；不把本轮接受写成永久豁免 |

> **"何时补"解决追踪，"阻断 / 可接受"解决能不能算完。** 一个写着"下个切片补"的缺口，**这一轮就是没做完**。

# 规格自检（下发前必做）

规格里的矛盾不会被自动发现——**靠的是运气**：工人恰好撞上并上报，才暴露出来。四问针对的就是这类。

> **未做对照验证**：本步骤的四问是推论，不是实测。

| 检查 | 反例（真实发生过的） |
|---|---|
| **可判定吗？** 一条要求若不能用"跑个命令看输出"或"读代码看结构"判真假，它就不是规格，是愿望 | "实现得优雅一点" ✗ |
| **有没有两条互相冲突？** | "掩码必须幂等" + "长度 < 8 时只输出指纹" ⇒ 8 位 hex 输入上冲突，导致合法密钥被明文放行 |
| **签名与散文一致吗？** 函数签名、类型、字段列表，与正文描述必须是同一件事 | 正文写"返回被清除的条数"，签名写 `-> Result<()>`；正文列 8 个字段，契约文档列 7 个 |
| **规格里凡涉及"用某个库 / 工具做某件事"，我核实过它真能做吗？** 断言必须落到**源码、文档或一次实测**，不能凭 crate 简介、类比或旧行为推断 | "PNG 等级 1–3 输出索引格式"——而所用的库没有索引编码路径 ⇒ 规格与依赖能力冲突，无法按此规格实现 |

**额外必查**：

- **清单类内容只允许一处权威**（字段表、端点表、参数表）——两处清单必然漂移。
- **类型决策要显式**（`Option<T>` 还是 `T`？谁负责归一化时区？），否则工人各处理一遍。
- **规格未覆盖的细节**要写明处置边界，按 `templates/AGENTS.md §1` 区分可逆内部选择与需报告的行为缺口。

## 独立契约复核（规格自检之后、闸门 A 之前）

派一个**未参与起草、只读**的子代理，给它契约草稿、原始需求及本次用来提取行为的材料；重写任务中，这些材料可包含旧实现，**复核者的读取范围由我在复核指令里明确列出，不等于授权实现工人读旧实现**。不要只给它我的结论或预期答案。

**做不做按档位定**：heavy 必做，lite 可省（档位判据见 `SKILL.md`「档位」）。

从 lite 升为 heavy 且尚未复核时，先对当前契约补做复核，再继续受影响的切片；发现的问题按闸门 B 处理。

让它逐条找：**需求是否遗漏、旧行为是否缺少「保留 / 修正 / 废弃」的裁决、条款是否冲突或无法判定、失败分类与类型决策是否缺失**。每个问题须给出契约位置、需求或源码出处、会失败的具体情形；没有证据的疑虑列为待核实，不当作缺陷。复核者不改契约，也不替我决定保留哪种旧行为。

保存复核原文与我的逐项裁决（heavy 按下文「流水」，lite 存总纲或附件）；台账为复核者登记 id、角色、所审契约的版本标识及裁决记录位置，切片、来源分支/补丁、实现基线、交接、整合和退回次数等实现字段填「不适用」。影响当前范围内行为判定的问题必须解决后才能冻结方案并派工；其余疑虑写明接受、待核实或移出范围的理由。无问题的复核也要留记录，但不能据此声称契约完整。环境不支持所需独立复核时，记录能力缺口，不把主代理自检写成独立复核；受阻的实现不越过该门槛。

**修订后的复核分两种，不要混为一谈**：① **核对已列问题是否关闭** —— 原复核者可续接时由它做；否则把原问题与证据交给新复核者。② **重新寻找盲点**（契约被实质性改写）—— 换一名**未参与起草、也未参与前次复核**的子代理。①只确认已列问题是否解决，不承担发现新盲点。此步骤不替代我的规格自检与最终验收。

# 记录系统

> **判据：这份文档能回答一个在流程里真的会被问的问题吗？** 文档没人读就是负债。

## 目录布局（唯一定义）

```
<repo>/                       被构建仓库 —— 与记录目录**同一个 git 仓库**
  AGENTS.md                   仓库工程约定（保留并合并现有要求）
  docs/<契约>.md              仓库内契约（**工人唯一的行为判据**）
  docs/freeze-plan.md         冻结方案（只保留当前有效范围）
  orch-doc/                   记录目录
    00-总纲.md  01-决策记录.md  02-切片计划.md  03-派工协议.md
    80-已知缺口.md  90-工人台账.md  99-完成总结.md
    prompts/    下发的指令          handoffs/  交接（**工人唯一可读**）
    流水/       每轮转录快照 + 裁决记录   验收/  我跑出的证据
    整合/       复杂整合时按批记录（可选）
```

上图是 heavy 的拆分布局。**lite 只建 `orch-doc/00-总纲.md` 与 `orch-doc/handoffs/`**，内容下限见下文「lite 记录」；下文的 ADR、缺口表、台账、验收等名称在 lite 指总纲内的记录。工人合同随指令下发；两档都保留仓库内契约与冻结方案。

### lite 记录

总纲保留当前范围与预算的索引、切片进度、工人 id 与基线和改动归属、验收结论及证据位置、未完成/未验证项及下一步。有行为或范围变更时记录决定、影响及代价；没有事件的可靠性栏、被否决方案、规模统计等字段可省，不沿用 heavy 的全部节次。

冻结方案和交接也可删掉无关示例、空表或已由权威文件说明的重复字段。不省略实际适用的授权与材料边界、验收判据、预算或阻断项；保留必要证据，允许用索引代替复制输出。给工人的索引须符合 `templates/AGENTS.md §1` 的读取边界。验收记录按 `references/verification.md` 执行，模板节次可合并。

**四条不变量**（换布局也要满足）：**① 记录目录被版本化**（才能把记录与代码状态对应）· **② 工人能读到 `handoffs/`**（否则跨轮交接断链）· **③ 契约与冻结方案在仓库内**（放记录目录里工人读不到硬约束）· **④ 契约在派活之前存在**（否则工人只能猜）。

**实现工人的读取边界见 `templates/AGENTS.md §1`**。主代理可读取全部记录；只读复核者按复核指令读取材料。派活时只下发所需材料，不通过完整对话继承把禁读记录带入工人上下文。

> **这条是纪律，不是机制——别把它当隔离。** 共享工作区内的文件读取约定不提供访问控制；是否有工具或文件系统隔离，以实际环境能力为准。

**怎么核对**：读取本环境可用的工人原始转录，核对初始上下文与工具调用实际覆盖的读取范围，包括工作目录、递归搜索、通配符、脚本及工具输出。命令未直接点名禁读路径，不足以证明未读取；范围无法还原或缺少等价审计能力时标为未验证。需要严格隔离时，用仅包含允许材料的工作区或工具访问限制，并核对初始上下文。

> ⚠ **只查流水与交接的文本会漏**——工人读了不一定提它，文本层可能没有任何痕迹。

**派活时只下发工人读取边界允许的记录**；边界见 `templates/AGENTS.md §1`，行为约束先同步到仓库内契约或本轮指令。

## 文档角色（份数按档位定，见 `SKILL.md` 档位表）

| 文档 | 回答的唯一问题 | 不写它会怎样 |
|---|---|---|
| **契约 `docs/<契约>.md`** | **正确的行为是什么**（编号的不变量 / 失败分类 / 类型决策） | **工人只能按最小做法猜**——最隐蔽的失败 |
| 总纲 | 当前边界 / 主代理从哪里恢复 / 决策与证据索引 | 换会话后难以确认下一步和在途工作 |
| 决策记录（ADR） | 为什么这么定 / **否掉了什么** | 已决之事被重新争论；作废决策被继续引用 |
| 切片计划 | 交付单位是什么 / 每片的验收标准 | "做完了"没有判据 |
| 派工协议 | 怎么派活 / 怎么验收 / 何时换工人 | 派活质量随机，验收靠感觉 |
| **缺口表** | 哪些没做 / 为什么 / **何时补** | **缺口丢失——最隐蔽的失败** |
| 工人台账 | 谁做了什么 / 可不可靠 | 无法判断该给多大自由度 |
| 流水 | 原始指令与原始产出 | 只看得到结论，看不到过程 |
| 验收 | **我亲自跑出的证据** | 采信自述 |
| 交接文档 | 跨轮传递什么 | 换工人就丢上下文 |
| 完成总结 | 交付了什么 / 凭什么说它是好的 / **哪些没验证** | 读者会把"检查全绿"读成"能用" |
| 整合记录（有复杂整合时） | 哪些来源落到哪个目标状态 / 冲突怎样裁决 / 验证在哪里 | 来源产物通过被误当作目标状态通过 |

**台账信息在任何档位都保留**，lite 可按目录布局合并；可靠性判断结合实际改动、验收与事件记录。

**这是下限，不是上限。** 按项目实际情况补充，但每加一份都要过同一个判据：**它回答哪个"在流程里真的会被问"的问题？** 答不上来的不加——**加一份无用文档比少一份更糟**，它会稀释"哪份该读"的判断，让整套文档一起被忽略。

典型需要补充的情形（给的是**判据**，不是一份必加清单）：要维持的**外部契约** → 契约文档；**性能或容量目标** → 基准台账；**实验性探索** → 实验日志；**数据或 schema** → 数据契约；**对外交付或多人协作** → 变更记录 / 发布说明；**合规、安全或许可约束** → 约束清单。

## 恢复入口

两档总纲都保留一个当前入口：有效契约与冻结方案的路径和版本、目标工作区与状态记录、切片进度和验收索引、在途工人的台账及状态核对入口、授权与剩余预算的出处、阻断项与下一步。只索引权威记录，不复制一套决策或授权；更新时间及仍待核实的状态写清楚。恢复时的实际核对见 `references/verification.md`「我自己的上下文」。

## 切片状态与整合记录

切片计划分别记录下列事实，lite 放总纲；每栏带所对应的状态标识与证据位置，不合成一个无对象的「完成」：

| 事实 | 可用状态 | 判据 |
|---|---|---|
| 工人交付 | 未交付 / 已交付 | 交接已定位到可取得的产物；不是采信「写完了」 |
| 产物验收 | 待验收 / 通过 / 退回 / 待重验 | 主代理在该来源状态完成规定验收 |
| 整合 | 未整合 / 已整合 / 已在目标工作区 | 来源到目标的对应关系已记录，或本就在共享目标工作区 |
| 目标验收 | 待验收 / 通过 / 不通过 / 待重验 | 整合后的目标状态完成规定门禁与适用流程验证 |

工人自报交付不等于产物验收通过，已整合不等于目标验收通过。后续变更使当前证据不再适用时，受影响的验收栏改为待重验并指向原记录，保留当时的结论。产物与目标确属同一状态时可引用同一份验收证据，复用条件见 `references/verification.md` 第 1 步。

整合记录保存批次与所含切片、来源产物及其交接/验收索引、目标整合前的基线与既有差异、来源提交或补丁标识到目标结果的对应关系、冲突裁决或额外修改、整合结果及目标验收出处。来源 SHA 不因目标提交身份变化而覆盖；来源与结果不必一一对应，以实际改动核对归属，方法见 `references/verification.md` 第 2 步。失败或撤回时追加当前结果、保留的目标状态和下一步，不抹掉尝试记录。整合执行与失败保护见 `references/delegation.md`「整合工人产物」。

共享工作区或一次简单整合可把这些内容放进现有验收记录。多个独立工作区分批整合、冲突或来源映射难以在一份验收中看清时，才建 `orch-doc/整合/`，每批一份记录；台账与切片计划只索引这份对应关系。记录仍属主代理视角，不扩大工人的读取范围。

## heavy 文档必含的节

| 文档 | 必含 | 关键点 |
|---|---|---|
| 契约 | **编号的不变量** / 失败分类 / 类型决策 / 未覆盖细节的处置 | 编号是工人引用它的方式（切片指令的"本轮要守的不变量"就指这里）。来源与产生时机见 `SKILL.md`「契约规格」 |
| 总纲 | 目标 / **范围与变更史（索引）** / 非目标 / 运营模型 / 目录约定 / 恢复入口 | 恢复入口内容见本文件对应节，不另维护第二套当前状态 |
| ADR | 背景 / 决定 / 理由 / **备选与代价** / 影响 | 缺"备选与代价"，决策无法翻案。被推翻时**追加"修订"节，不改原文** |
| 切片计划 | 进度总览（按「切片状态与整合记录」区分状态并带证据出处）/ 验收标准索引 | 标准以冻结方案为准，不另维护副本 |
| 派工协议 | 本环境的派工形态 / 指令模板指针 / 工人 id 命名与登记规则 / 交接模板指针 / 验收协议 / 退回协议 / 台账登记规则 | lite 直接使用本轮指令，不另建协议文档 |
| 流水 | **每轮转录快照**（`<工人 id>-<时间戳>.md`，取自本环境可用的原始转录）+ **我的裁决记录**（`<工人 id>-轮<k>.md`） | 原件不改写；入库副本的敏感信息处理见下。快照落盘后可版本化；裁决记录区分实现问题与规格问题。拿不到原始转录时保留可得产出并标明审计缺口，不编造转录 |
| 完成总结 | 交付物 / 规模 / 架构 / 正确性证据 / 真实缺陷 / 方法 / **未完成与未验证（单独成节）** / 如何继续 | "未验证"混进正文，读者就会把"检查全绿"读成"能用" |
| 缺口表 | 待补（`缺口 / 来源 / 影响 / **何时补** / **阻断？**`）/ 已消除 / 记录规则 | 空话不入表。"何时补"写成触发条件；**"阻断？"决定它能不能算完**（判据见闸门 D）——不写这一列，"完成"就退化成填表 |
| 工人台账 | **工人 id 与角色** / 切片 / 工作区及来源分支或补丁位置 / **派工前的基线状态（SHA + `git status` + 已有差异）** / 轮数 / **状态** / 交接 / 退回次数 / 整合记录索引；可靠性与事件记录 | 工人的「已验收」只指产物验收；切片目标验收另见切片计划。中断、超时、废弃单独记；复核者不适用的实现字段按独立复核规则填写 |
| 整合记录（可选） | 内容见「切片状态与整合记录」 | 简单整合复用验收记录，复杂整合才拆文件 |

版本化的流水不得包含凭据或个人信息。若原始转录含敏感内容，只提交标注删节的副本；能保留原件时在裁决记录注明其受控位置，不能保留时明确标记该轮审计证据不完整。

**两份通用纪律**（各自的权威不在这里，这里只是索引）：验收证据先产生再记录（见 `references/verification.md`）；按仓库约定划分提交并显式暂存路径（见 `templates/AGENTS.md §5`）。

> **`验收` 与 `交接文档` 的节次定义在各自模板里**（`templates/acceptance.md`、`templates/prompt-slice.md` 文末），本表不复制。

## 反模式

**叙事式流水账**：写"我们讨论了 X 然后决定 Y"——没人会读第二遍。要的是**结论 + 判据**。
