# 闸门与记录系统

> **每个闸门都有固定形状的工件**——没有工件，闸门会退化成"我觉得可以了"。

## 闸门 A · 方案冻结

工件 = `templates/freeze-plan.md`，**落盘在被构建仓库的 `docs/freeze-plan.md`**——工人只读「仓库内文件 + 交接目录」，放进记录目录里工人就读不到边界。

两条最常被省掉的：

- **非目标**——比目标更能防范围漂移。
- **本机无法验证清单**——**冻结时就写**，不要收尾才发现。否则用户会把"检查全绿"读成"能用"。

**必须同时定下预算断路器**（冻结方案 §8）：连续多少个窗口失败就停下重估、最多投入多少轮/多久。**没有断路器的流程不会停**——它会一直"再试一个窗口"，直到用户叫停。

形态（已授权 ⇒ 通报 / 未授权或不可逆或代价超预算 ⇒ 停下等）与档位共定见 `SKILL.md`「闸门」。**沉默不是同意。**

## 闸门 B · 变更（带代价核算）

范围或架构一旦变更，**先产出三样**（这一步无条件做）：① **一条 ADR（唯一定义，写在 `doc/01-决策记录.md`）** ② **作废清单**（哪些既有决策 / 文件 / 计划失效）③ **代价核算**（作废了多少已完成工作、已花多少轮次）。

**只有影响用户承诺 / 成本 / 权限的变更才需要用户决定**——改变了交付范围、增加了花费、动了权限或外部可见契约。**纯内部的架构调整（同样记 ADR）通报即可，不要为它停工。**

> **变更史只在一处**：ADR 是权威；总纲的「范围与变更史」是**索引**（一行一条，指向 ADR）；`docs/freeze-plan.md` **只保留当前有效的目标与非目标**，不留变更史。三处都写必然漂移。

**不核算代价的变更 = 让用户闭着眼付账。**

> **变更若改了工人要遵守的约束**（契约里的不变量、失败分类、目录边界），必须**同时更新 `docs/<契约>.md` 或 `docs/freeze-plan.md`**——ADR 在 `doc/` 里，工人读不到（见 `templates/AGENTS.md §1`）。只写 ADR 等于没通知工人。

## 闸门 C · 切片收尾（默认不问用户）

产出 = 验收记录（`templates/acceptance.md`），**只能由命令输出填充**。

**这一关由我跑全量门禁**（做法与理由见 `references/verification.md` 第 1 步）——工人的检查限定到本包，所以**只有我能做累积回归**。

**默认不问用户**——每片都问会让人厌烦，反而促使你跳过闸门 A。只有两种情况例外：该片触及**不可逆操作**（删数据、改 schema、发布、改权限），或改变**用户可见契约**（命令行参数、配置文件格式、对外接口）。

## 闸门 D · 最终验收（**交付，不是再等一次批准**）

① 全量门禁的真实输出（**最后一次复跑**，不是中间某次的）② **未验证清单逐条交付**，每条写清"为什么没验"与"怎么才能验" ③ **完成定义判定**：达标报「完成」，有阻断项报「**部分完成**」。

这一关**不设等待**——A 已经授权过，B 管变更，D 只是把结果交出去。用户看到「部分完成」或未验证清单后自行决定下一步。

**完成定义**：

- [ ] 每个切片验收通过
- [ ] **没有阻断项**（见下）
- [ ] 未验证清单已交付用户

**缺口分两类，只有一类阻断完成**：

| 类 | 判据 | 对"完成"的影响 |
|---|---|---|
| **阻断** | **未满足当前验收标准**的缺口 | **阻断**。此时只能报「**部分完成**」——**即使每项都写了"何时补"** |
| **可接受** | 已**明确移出当前范围**，或用户**已接受的限制** | 不阻断，写「永久接受 + 理由 + 谁接受的」 |

> **"何时补"解决追踪，"阻断 / 可接受"解决能不能算完。** 一个写着"下个切片补"的缺口，**这一轮就是没做完**。

# 规格自检（下发前必做）

一次真实运行中，下发的规格里有 **4 处自相矛盾**，全部由工人发现上报——**靠的是运气**。那 4 处都落在下面三类里。

> **未做对照验证**：本步骤的三问是推论，不是实测。

| 检查 | 反例（真实发生过的） |
|---|---|
| **可判定吗？** 一条要求若不能用"跑个命令看输出"或"读代码看结构"判真假，它就不是规格，是愿望 | "实现得优雅一点" ✗ |
| **有没有两条互相冲突？** | "掩码必须幂等" + "长度 < 8 时只输出指纹" ⇒ 8 位 hex 输入上冲突，导致合法密钥被明文放行 |
| **签名与散文一致吗？** 函数签名、类型、字段列表，与正文描述必须是同一件事 | 正文写"返回被清除的条数"，签名写 `-> Result<()>`；正文列 8 个字段，契约文档列 7 个 |

**额外必查**：

- **清单类内容只允许一处权威**（字段表、端点表、参数表）——两处清单必然漂移。
- **类型决策要显式**（`Option<T>` 还是 `T`？谁负责归一化时区？），否则工人各处理一遍。
- **规格未覆盖的细节**要写明"按最小做法决定并记录"——否则工人会去猜、或去找别处抄。

# 记录系统

> **判据：这份文档能回答一个在流程里真的会被问的问题吗？** 文档没人读就是负债。

## 目录布局（唯一定义）

```
<repo>/                       被构建仓库 —— 与记录目录**同一个 git 仓库**
  AGENTS.md                   工人合同
  docs/<契约>.md              仓库内契约（**工人唯一的行为判据**）
  docs/freeze-plan.md         冻结方案（只保留当前有效范围）
  doc/                        记录目录
    00-总纲.md  01-决策记录.md  02-切片计划.md  03-窗口协议.md
    80-已知缺口.md  90-窗口台账.md  99-完成总结.md
    prompts/   下发的指令      handoffs/  交接（**工人唯一可读**）
    流水/      驱动器原始输出 + 裁决记录     验收/  我跑出的证据
```

**四条不变量**（换布局也要满足）：**① 记录目录被版本化**（否则"文档与代码分开提交"无从执行）· **② 工人能读到 `handoffs/`**（否则跨窗口交接断链）· **③ 契约与冻结方案在仓库内**（放记录目录里工人读不到硬约束）· **④ 契约在派活之前存在**（否则工人只能猜）。

**⚠ 工人不得读 `doc/` 的其余部分**——总纲 / 决策记录 / 缺口表 / 台账 / 流水 / 验收都是**架构者视角**（未定的决策、对工人表现的记录、我自己的失误），读到会污染它的判断。**只有 `doc/handoffs/` 允许它读。**

> **这条是纪律，不是机制——别把它当隔离。** `doc/` 就在被构建仓库里，也就是工人的工作目录里，**它本来就完全可读**。驱动器的 `--add-dir` 语义是"**追加**一个工作区目录"（`omp --help` 原文：*Add a workspace directory beyond the working directory*）——**只增不限**，对已在工作目录内的文件毫无隔离作用。要真正隔离只有两条路：把记录目录放到仓库之外（会破坏不变量 ①③），或换一个支持拒绝读的 CLI。**在现状下唯一的作用力是工人合同里的约定，加上我在验收时核对它有没有越界读。**

## 文档角色（份数按档位定，见 `SKILL.md` 档位表）

| 文档 | 回答的唯一问题 | 不写它会怎样 |
|---|---|---|
| **契约 `docs/<契约>.md`** | **正确的行为是什么**（编号的不变量 / 失败分类 / 类型决策） | **工人只能按最小做法猜**——最隐蔽的失败 |
| 总纲 | 做什么 / 不做什么 / **范围变过几次**（索引，指向 ADR） | 范围漂移后没人知道当前边界 |
| 决策记录（ADR） | 为什么这么定 / **否掉了什么** | 已决之事被重新争论；作废决策被继续引用 |
| 切片计划 | 交付单位是什么 / 每片的验收标准 | "做完了"没有判据 |
| 窗口协议 | 怎么派活 / 怎么验收 / 何时换窗口 | 派活质量随机，验收靠感觉 |
| **缺口表** | 哪些没做 / 为什么 / **何时补** | **缺口丢失——最隐蔽的失败** |
| 窗口台账 | 谁做了什么 / 可不可靠 | 无法判断该给多大自由度 |
| 流水 | 原始指令与原始产出 | 只看得到结论，看不到过程 |
| 验收 | **我亲自跑出的证据** | 采信自述 |
| 交接文档 | 跨窗口传递什么 | 换窗口就丢上下文 |
| 完成总结 | 交付了什么 / 凭什么说它是好的 / **哪些没验证** | 读者会把"检查全绿"读成"能用" |

**台账在任何档位都不能省**——它是判断工人可靠性的唯一依据。

**这是下限，不是上限。** 按项目实际情况补充，但每加一份都要过同一个判据：**它回答哪个"在流程里真的会被问"的问题？** 答不上来的不加——**加一份无用文档比少一份更糟**，它会稀释"哪份该读"的判断，让整套文档一起被忽略。

典型需要补充的情形（给的是**判据**，不是一份必加清单）：要维持的**外部契约** → 契约文档；**性能或容量目标** → 基准台账；**实验性探索** → 实验日志；**数据或 schema** → 数据契约；**对外交付或多人协作** → 变更记录 / 发布说明；**合规、安全或许可约束** → 约束清单。

## 每份文档必含的节

| 文档 | 必含 | 关键点 |
|---|---|---|
| 契约 | **编号的不变量** / 失败分类 / 类型决策 / 未覆盖细节的处置 | 编号是工人引用它的方式（切片指令的"本轮要守的不变量"就指这里）。来源与两种模式见 `SKILL.md`「契约规格」 |
| 总纲 | 目标 / **范围与变更史（索引）** / 非目标 / 运营模型（我是什么、工人是什么）/ 目录约定 | 只留最新版，就答不了"当初为什么改" |
| ADR | 背景 / 决定 / 理由 / **备选与代价** / 影响 | 缺"备选与代价"，决策无法翻案。被推翻时**追加"修订"节，不改原文** |
| 切片计划 | 进度总览（状态列**带验收证据出处**）/ 各片验收标准（可跑的命令 + 期望） | "已验收"没有出处就只是自称 |
| 窗口协议 | 驱动命令 / 指令模板指针 / 上下文预算规则 / 交接模板指针 / 验收协议 / 退回协议 / 台账登记规则 | 它是**流程的可执行定义**；没有它，每个窗口的派活质量靠临场发挥 |
| 流水 | **驱动器原始输出**（`W<n>-<时间戳>.txt`，只引用不得改写）+ **我的裁决记录**（`W<n>-轮<k>.md`） | 加工过的流水失去审计价值。裁决记录里**必须分开"工人出错"与"我写坏规格"** |
| 完成总结 | 交付物 / 规模 / 架构 / 正确性证据 / 真实缺陷 / 方法 / **未完成与未验证（单独成节）** / 如何继续 | "未验证"混进正文，读者就会把"检查全绿"读成"能用" |
| 缺口表 | 待补（`缺口 / 来源 / 影响 / **何时补** / **阻断？**`）/ 已消除 / 记录规则 | 空话不入表。"何时补"写成触发条件；**"阻断？"决定它能不能算完**（判据见闸门 D）——不写这一列，"完成"就退化成填表 |
| 窗口台账 | 窗口 / 切片 / session / **开窗前的基线状态（SHA + `git status` + 已有差异）** / 轮数 / **状态** / 交接 / 退回次数；**工人可靠性记录**；事件记录 | **基线状态是验收第 2 步归因的前提**——共享分支上 `基线..HEAD` 混着别的窗口的提交，不记就无法把改动归给谁。状态词要有区分度：`已验收` / `中断`（进程消失）/ `超时`（撞上限）/ `已废弃`——混成一个"失败"就丢掉最有价值的信息 |

**两份通用纪律**：验收类内容只能由命令输出填充（「跑 → 贴」）；代码与文档分开提交。

## 反模式

**叙事式流水账**：写"我们讨论了 X 然后决定 Y"——没人会读第二遍。要的是**结论 + 判据**。
