# 派活：先分清委托的目的

**委托有两种目的，判据完全不同。先问自己"我要的是产出物，还是结论"。**

| 目的 | 你要的东西 | 详见 |
|---|---|---|
| **生产型** —— 让别处把活干出来 | 交付物（代码、文档、修复） | 本文「生产型」节 |
| **隔离型** —— 让别处烧掉上下文，只带回结论 | 压缩后的结论 + 出处 / 实验 / 真实响应 | 本文「隔离型」节 |

> 并行修多个互不干扰的独立 bug，是生产型的一个特例——按问题域分片即可，不需要另立流程。

---

# 生产型：工人 = 子代理

**载体是子代理**：`task`（批量走 `tasks[]`，`context` 装共享背景）、或需要脚本编排时用 `eval` 的 `agent()` / `workpool()`。

下列 OMP 接口、状态和默认值是已有用法记录，**当前版本未核实**。使用前核对本环境工具文档或实际能力；不可直接当作其他 harness 的执行指令。无法取得完整转录时，明确留下审计缺口。

| 事 | 形态 |
|---|---|
| 读什么 | 见 `SKILL.md` 纪律 2 |
| **续接** | `hub` `send` 给已 `parked` 的工人会**复活**它——`task` 没有 resume 参数，消息是唯一的续接原语 |
| **中途纠正** | 同样用 `hub` `send`：注入为非中断性旁注（steering），回复是真实回合；`await: true` 阻塞等它回一条 |
| 双向提问 | 工人可以反向 `hub` `send` 给我 |
| 结构化产出 | `outputSchema` + `schemaMode`（`permissive` / `strict`） |
| **审计** | `history://<id>`（简洁转录）· `agent://<id>`（最终产出）· `<id>.jsonl`（原始会话）· Agent Hub 实时看 |
| **隔离** | `isolated: true`：需 git 仓库，产出 patch 或 `omp/task/<id>` 分支；**完成即拆解、不可复活** |
| 并行上限 | `task.maxConcurrency`；后台作业不阻塞我的轮次 |

**OMP 上限示例**（使用前核实实际状态与续接能力）：

| 设置 | 默认 | 撞上之后 |
|---|---|---|
| `task.softRequestBudget` | 200 请求 | 1.5× 时**强制收尾**并 yield 部分结果 ⇒ 工人转 `idle`，**可续接** |
| `task.maxRuntimeMs` | `0`（关闭） | 到点中止 ⇒ 转 `aborted`，终态、不可续 |
| `task.agentIdleTtlMs` | 7 分钟 | `idle` 转 `parked`（会话保留）⇒ 发消息复活 |

撞上软预算后，若工人处于可续接状态，就用 `hub` `send` 下发窄任务（只修失败项 + 收尾）；`aborted` 或已拆解的隔离工人无法走这条路。

**记下工人的 id**（`task` 的 `name` 字段自定，默认是生成的 `AdjectiveNoun`）。id 是续接、取产出、审计三件事的入口——不记就等于关掉了这三件事。

## 复用工人还是启用新工人

**复用保留有效上下文；换人取得独立判断。** 同一问题的窄修复或紧密相连的后续工作，原工人仍可靠且可续接时复用；独立复核、需要摆脱已被证伪的假设，或原会话不可续接时换人。切片边界本身不决定是否换人。

换人前先按 `references/verification.md`「退回协议」排除规格问题；换人时记录原因与交接。新工人依据当前契约和可复核证据接手，不采信前任自述。

# 隔离型：让别处烧上下文，只带回结论

指令约束输出形状：结论在前、长度有界、每条带可定位出处。主代理取得压缩结论后只回读需要核对的材料。

## 该不该隔离

能低成本得出可核对结论就自己做；需要大量逐项理解或探索、而我只需要压缩后的结论与出处时才隔离。**材料在本地还是外部，不是判据。**

> **未做对照验证**：这条判据是设计推论，没有对照试验量化两侧的成本。

## 两条不能违反的

1. **避免重复整套探索。** 复核关键证据、重跑必要实验仍须做，但不无理由地重复已委托的全量阅读与搜索。
2. **先把结论当待核对的线索**；附带的源码、实验与原始响应用于复核，不把结论自述当成验证结果：
   - **调研** → 结论要能追溯到出处，我抽查关键结论
   - **实验** → **实验落盘在我能重跑的位置**——这一条把"它说它试过了"变成证据
   - **外部核验** → 留下**真实响应**（不是"文档上说"）
   - **审查** → 可定位的问题（文件 + 行 + 为什么），不是"看起来还行"

> **外部核验**的产物要求与熔断见 `references/verification.md`「外部核验的产物要求」——唯一定义在那里。

## 指令必须带上评判标准

给工人的背景明确列出本次问题、项目约束与评判标准，不依赖它继承完整对话。例如比较 A 与 B 时，写清本项目的正确性、兼容性或维护要求，而非泛泛比较优劣。

# 并行与共享可变资源

**这一节与载体无关**——多个工人同时改一个仓库时的纪律，换任何工具都成立。

| 问题 | 对策 |
|---|---|
| 同包 / 同目录的多个工人 | **文件集不相交、且都不改共享文件时可以并行**——代价是**一个工人的中间态会让另一个的检查假失败**（项目级检查命令是整包作用域）。同文件则必须串行。指令里要写明"先写完自己的文件，别长时间破坏可编译性" |
| 并行工人共享可变资源 | 同文件、同 schema、同 manifest、模块与依赖声明入口、Git 暂存区等可变资源的写入必须串行或有唯一 owner；入口文件的过期读取可能静默回退他人声明 |
| **同一仓库的并发提交** | `.git/index` 是**共享可变资源**：两个工人同时 `git add`/`commit` 会撞 `index.lock`，更糟的是 A 的提交会**扫进 B 已暂存的文件**。⇒ 同一仓库同一分支的工人**提交必须串行**。要真并行就各给一个 `git worktree` + 独立分支，由我合并——或直接用 `isolated: true` 让 harness 建工作区并回传 patch / 分支 |
| 工人越界改动 | 先报告；主代理核对行为、权限、代价与影响范围，再按闸门 B 决定接受或退回。技术上正确不自动获得授权 |

## 让工人产出可信的信号

值得在指令里明确鼓励这几类行为：

| 行为 | 为什么值钱 |
|---|---|
| **拒绝猜** | 规格有矛盾时**原样上报**，而不是选一边做下去 |
| **证伪自己的测试** | 例如：删掉被测的那行配置，看测试是否仍然通过——如果通过，说明测试证明的不是你以为的东西 |
| **拒绝把兜底条款执行成错的** | 指令的兜底分支若会破坏语义，**拒绝执行并说明理由** |
| **主动上报缺口** | 把没做的事具体到文件与函数 |

反过来，**采信这些自述就是失职**——见 `references/verification.md`。

**切片指令里最不能省的是「本轮约束」**（只许改哪些目录、是否禁止新增依赖、有没有不得触碰的资源）。

# 独立对抗读者（可选）

派一个**没有参与规格与派活**的工人，逐行读交付物 + 契约，只问三件事：① 哪里自相矛盾 ② 哪里与它自己声称的规则冲突 ③ 哪里会让执行者做错事。

**警惕信号**：我已连续多轮只看到"绿"而没看到过"红"——那通常意味着我的检查已经和我的盲区同构了。

> 同模型的不同视角仍可能出现相关错误，换人不保证判断独立。使用不同模型时按实际 harness 核对配置能力；不同模型能增加多少复核收益，**未做对照验证**。
